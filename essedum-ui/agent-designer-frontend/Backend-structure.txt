
​# Backend Architecture - AgentFlow Designer

## V1 Scope (MVP)

This version is limited to the following capabilities only:

- ChatInput node
- ChatOutput node
- Model node with providers:
  - Azure OpenAI
  - AWS Bedrock
  - Google Vertex AI
- Prompt Template node
- MCP Tool node
- RAG Agent node integrated with Qdrant Vector DB
- Memory node

Out of scope for V1:

- Auth and RBAC hardening beyond basic internal access
- Flow marketplace/templates publishing
- Advanced node categories (condition, generic tool router, agent planner loops, etc.)
- Hybrid reranking and advanced retrieval tuning
- Broad provider matrix beyond Azure OpenAI, Bedrock, and Vertex AI

## Tech Stack

| Layer | Technology | Rationale |
|-------|-----------|-----------|
| Framework | **FastAPI** | Async, type-safe, auto-docs, WebSocket support |
| ORM | **SQLAlchemy 2.0** (async) | Mature, flexible, async support |
| DB | **PostgreSQL** | JSONB for flow data, reliable, scalable |
| Vector DB | **Qdrant (V1)** | Single supported vector store for V1; adapter remains extensible for later providers |
| Cache | **Redis** | Sessions, execution state, pub/sub for WebSockets |
| Task Queue | **Celery + Redis** | Long-running flow executions & document ingestion |
| Model Providers | **Azure OpenAI / AWS Bedrock / Google Vertex AI** | Restricted provider set for V1 |
| Embeddings | **Provider-native embeddings + optional local HF** | Used by RAG agent for ingestion/query embeddings |
| Doc Parsing | **unstructured / PyMuPDF / python-docx** | PDF, DOCX, CSV, HTML parsing for RAG |
| Chunking | **LangChain TextSplitters** | Recursive, semantic, token-based chunking |
| Validation | **Pydantic v2** | Request/response models, settings |
| Migration | **Alembic** | Schema migrations |
| Testing | **pytest + httpx** | Async testing |
| Containerization | **Docker + docker-compose** | Dev/prod parity |

**Search Request Schema:**
```json
{
  "query": "What is the refund policy?",
  "top_k": 5,
  "score_threshold": 0.7,
  "filter": {
    "file_type": ["pdf", "docx"],
    "document_ids": ["uuid1", "uuid2"]
  }
}
```

**RAG Query Request Schema:**
```json
{
  "query": "Summarize the Q4 earnings report",
  "knowledge_base_ids": ["kb-uuid-1", "kb-uuid-2"],
  "llm_provider": "azure_openai",
  "llm_model": "gpt-4.1",
  "top_k": 5,
  "system_prompt": "You are a financial analyst assistant.",
  "include_sources": true,
  "stream": false
}
```

**RAG Query Response Schema:**
```json
{
  "answer": "Based on the Q4 earnings report, revenue increased by 15%...",
  "sources": [

      "document_id": "uuid",
      "filename": "Q4_earnings.pdf",
      "page_number": 3,
      "content": "Revenue for Q4 2025 was $2.3B, a 15% increase...",

    "retrieval_time_ms": 45,
    "generation_time_ms": 820,
    "tokens_used": { "prompt": 1800, "completion": 350 }
  }
}
```

## Execution Engine Design

```
┌───────────────────────────────────────────────────────────────┐
│                    EXECUTION ENGINE                            │
│                                                               │
│  1. VALIDATION                                                │
│     - Check all required fields configured                    │
│     - Verify credentials exist for external calls             │
│     - Detect cycles in graph                                  │
│     - Validate port compatibility                             │
│     - Verify KB exists for RAG/Vector Search nodes            │
│                                                               │
│  2. TOPOLOGICAL SORT                                          │
│     - Build DAG from nodes + edges                            │
│     - Identify execution layers (parallelizable groups)       │
│     - Detect independent subgraphs                            │
│                                                               │
│  3. EXECUTION (per layer)                                     │
│     - Nodes in same layer run in parallel (asyncio.gather)    │
│     - Each node invokes its category executor:                │
│       ┌─────────────────────────────────────────────┐         │
│       │  ChatInputExec    → capture user message     │         │
│       │  PromptExecutor   → template interpolation   │         │
│       │  ModelExecutor    → Azure/Bedrock/Vertex AI │         │
│       │  MCPExecutor      → invoke MCP tools         │         │
│       │  RAGExecutor      → retrieve + generate      │         │
│       │  MemoryExecutor   → read/write memory store  │         │
│       │  ChatOutputExec   → emit final response      │         │
│       └─────────────────────────────────────────────┘         │
│     - Output of node N feeds into input of downstream nodes   │
│                                                               │
│  4. ERROR HANDLING                                            │
│     - Per-node retry with exponential backoff                 │
│     - Configurable: fail-fast vs continue-on-error            │
│     - Timeout per node (default 60s, configurable)            │
│     - Circuit breaker for external API calls                  │
│                                                               │
│  5. LOGGING & STREAMING                                       │
│     - Every state change → WebSocket broadcast                │
│     - All logs persisted to execution_logs table              │
│     - Node outputs cached in Redis during execution           │
└───────────────────────────────────────────────────────────────┘
```

### Chunking Strategies

| Strategy | Best For | Config |
|----------|----------|--------|
| **Recursive Character** | General text (default) | chunk_size=512, overlap=50 |
| **Semantic** | Long-form docs where topic boundaries matter | embedding-based split detection |
| **Token-based** | LLM-aware chunking, precise token budgets | max_tokens=256, model-specific tokenizer |
| **Markdown/HTML** | Structured documents | Split on headers, preserve hierarchy |
| **Row-based** | CSV/tabular data | Each row as a chunk with column headers |

### Embedding Models Supported

| Provider | Model | Dimensions | Use Case |
|----------|-------|-----------|----------|
| Azure OpenAI | `text-embedding-3-small` | 1536 | Managed Azure stack |
| Bedrock | `amazon.titan-embed-text-v2:0` | 1024 | AWS-native deployments |
| Vertex AI | `text-embedding-005` | 768 | GCP-native deployments |
| HuggingFace (optional) | `all-MiniLM-L6-v2` | 384 | Local/dev fallback |

## Key Design Decisions

1. **Strict V1 feature gate**: Backend validates node types and rejects graphs containing non-V1 nodes.
2. **Async-first runtime**: All I/O operations use async/await for parallel node execution where possible.
3. **Provider restriction by design**: Model connector layer only exposes Azure OpenAI, Bedrock, and Vertex AI.
4. **RAG-first retrieval**: RAG Agent is first-class and backed by Qdrant in V1.
5. **Memory persistence**: Memory node reads/writes scoped conversational state for multi-turn continuity.
6. **Execution streaming**: WebSocket remains mandatory for node-level runtime visibility.
7. **Flow graph in JSONB**: Node/edge definitions remain schema-flexible while still versionable later.
8. **Extensible but disabled-by-default**: Extra node categories stay behind a future-version feature flag.
